## 一、定位澄清

**MimirAether 不是"飞书 AI"。**

MimirAether 是一个**独立存在的 CLI Agent 平台**，飞书只是它的第一个接入点（channel）。它的定位是：

```
MimirAether = Agent Core（核心）+ 多平台 Channel（飞书/CLI/...）
```

**未来目标**：CLI 为主平台，可以拓展 Discord、Telegram、Email 等其他 channel。当前飞书是第一个 channel，不是它的本质。

**学习对象**：
- **Hermes**（ Nous Research）— 多平台架构、Skills 自积累、provider agnostic
- **pi-agent**（pi.dev）— 高质量代码执行、结构化架构、60%+ 测试覆盖

## 四、工程质量为什么这么低？

### 4.1 测试覆盖率只有 5% 的可能原因

1. **GOD 类文件未拆分** — 核心逻辑集中在少数大文件（如 `core_loop.py` 3000+ 行），导致测试无法精准覆盖
2. **工具执行路径未充分 Mock** — 大量 `exec`、`subprocess` 调用依赖真实环境，单元测试难写
3. **历史债务** — 开发过程中优先功能交付，测试建设滞后
4. **上下文三重管理互相抵消** — `conversation_history` + `context_compressor` + `recovery` 三套系统存在重叠，降低了可测试性
5. **自进化优先级高于测试** — 团队资源向 SELF-LOOP 倾斜，测试基础设施投入不足

### 4.2 pi-agent 能做到 60%+ 的关键

pi-agent 的架构设计从一开始就把可测试性纳入核心：
- **Monorepo + 清晰包边界**（packages/agent、packages/ai、packages/coding-agent）
- **工具层与核心逻辑分离** — 工具是纯函数，易于 Mock
- **小而专注的包** — 每个包职责单一，测试粒度细

## 五、改造方向建议

### 5.1 测试覆盖率：从 5% 提升到 50%+（第一优先级）

**目标**：3 个月内测试覆盖率从 5% 提升到 50%。

**实施路径**：

| 阶段 | 目标 | 关键动作 |
|------|------|---------|
| **Phase 1**（1~2周） | 15% | 将 `tools/registry.py`、`agent/credential_pool.py` 等独立模块独立测试，目标 80% 覆盖 |
| **Phase 2**（3~6周） | 30% | GOD 拆分后逐包测试，重点：`core_loop.py` 拆分出的核心函数 |
| **Phase 3**（6~12周） | 50% | 完整 `agent/` + `gateway/` 覆盖，达到 pi-agent 同等水平 |

**关键技术手段**：
- 工具层用 `unittest.mock` 隔离真实 subprocess 调用
- Monorepo 化改造（参考 pi-agent 的 `packages/` 结构）
- CI 强制覆盖率门禁（覆盖率 < 50% 禁止 Merge）

### 5.2 架构重构：GOD 拆分

**问题**：`core_loop.py` 3000+ 行，是所有架构问题的根源。

**方案**：参照 pi-agent 的 `packages/` 模式，将 GOD 类文件拆分为独立包：
```
agent/core_loop.py   →   agent/loop/ + agent/intent/ + agent/exec/
tools/               →   tools/registry.py 保持，工具实现下沉
gateway/             →   平台无关 + 平台 adapter 分离
```

**参考**：pi-agent 的 packages/agent（核心）+ packages/ai（模型层）+ packages/coding-agent（场景层）

### 5.3 验证门禁：修复编造问题（P0 优先级）

**今天（2026-06-01）刚刚讨论过的问题**：Mimir 在跨 session 后会编造未完成的操作。

**解决方案**（详见 `output/2026-05-28-琬弦-MIMIR编造问题修复方案.md`）：

| 优先级 | 方案 | 效果 |
|--------|------|------|
| **P0** | IntentPredictor 修正 | 续执行任务强制调工具验证 |
| **P1** | C1 消息优先级排序 | 长期对话不丢 tool result |
| **P2** | Verification Gate | 宣称完成前必须调验证工具（架构层） |

### 5.4 多平台架构：向 Hermes 学习

**现状**：Mimir 只有飞书 channel，平台耦合在 gateway 层。

**目标**：将 channel 层解耦，支持：
- 飞书（当前）
- CLI（未来）
- Discord / Telegram / Email（待拓展）

**参考 Hermes 的 platform/gateway 分离架构**。

### 5.5 Provider 抽象：向 pi-agent 学习

**现状**：Mimir 主要用 DeepSeek，Provider 切换成本高。

**目标**：实现 pi-agent `packages/ai` 级别的 provider 抽象，支持 OpenAI / Anthropic / DeepSeek / Google 等无缝切换。

## 六、测试覆盖率专项分析

### 6.1 当前问题

- 测试覆盖率 **5%**，严重不足
- `core_loop.py`、`exec_mixin.py` 等核心文件几乎无测试
- 大量 `try/except` 空 catch，错误被静默吞掉

### 6.2 为什么重要

| 风险 | 后果 |
|------|------|
| **重构恐惧** | 代码不敢改，改了不知道会不会挂 |
| **回归率高** | 每次 SELF-LOOP 进化后旧功能出错 |
| **编造温床** | 没有测试的路径，最容易产生虚假结果（今天的编造问题与此相关）|
| **调试困难** | 问题只能在运行时暴露，定位成本高 |

### 6.3 改造建议

1. **引入 pytest + pytest-cov**，在 CI 中强制覆盖率报告
2. **工具层先行**：`tools/` 下每个工具独立测试，目标 90% 覆盖
3. **核心层 Mock**：用 `unittest.mock` 替代真实 `subprocess` 调用
4. **GOD 拆分后测试**：拆出来的每个函数独立测试
5. **覆盖率门禁**：PR Merge 前覆盖率不得低于当前值，持续提升

## 八、结论

MimirAether 是一个**有野心的自进化 Agent 平台**，核心亮点是 SELF-LOOP 任务链和元认知能力。但在工程质量（6.2）和测试覆盖（5%）方面存在明显短板，这正是它向 Hermes 和 pi-agent 学习时需要补上的课。

**当前最紧迫的事**：测试覆盖率提升和编造问题修复。这两件事直接影响 Mimir 的可靠性和自我进化质量。
