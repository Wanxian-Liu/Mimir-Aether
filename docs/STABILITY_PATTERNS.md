# MimirAether 稳定性设计模式

> **来源**: LeWM (2603.19312) §3.1 SIGReg + §5.2 VoE | 2026-05-14
> **原则**: 用结构约束替代数字阈值。不是"调参数让系统稳定"，而是"让不稳定在数学上不可行"

---

## 1. 核心原则

| # | 原则 | LeWM 来源 | MimirAether 映射 |
|---|------|----------|-----------------|
| 1 | **结构约束 > 数字阈值** | SIGReg 强制高斯潜变量，1个参数替代6个 | `info_density_min` 单参数替代 3 阈值 |
| 2 | **语义意外 ≠ 表面意外** | VoE: 物理不可行事件的 surprise 显著高于视觉变化 | Surprise Gate: 格式变化忽略，语义矛盾触发重规划 |
| 3 | **优雅降级 > 崩溃** | JEPA 无 EMA/辅助监督仍可训练（只是慢） | 三级回退链: HTML Card → 降级文本 → Markdown |
| 4 | **检测分离于执行** | SIGReg 是被动约束，不参与梯度 | degeneration-guard 是独立通道，不影响主循环 |
| 5 | **恢复有上限** | N/A (LeWM 是训练框架) | recovery_loop: 3次恢复+2种错误→系统性问题→重规划 |

## 3. 设计模式

### 3.1 单参数门控 (SIGReg 模式)

**问题**: 多阈值配置容易产生"阈值交互地狱"——改一个阈值影响另一个的判断逻辑，全局行为不可预测。

**模式**: 用一个结构性参数替代多个数字阈值。

```
❌ 反模式:
  threshold_turns: 4      ← 改这个影响 window_size
  min_unique_tools: 2     ← 改这个影响误报率
  min_file_ops: 1         ← 改这个影响漏报率
  → 3个参数，3³=27种组合，行为不可预测

✅ SIGReg 模式:
  info_density_min: 0.4   ← 单参数: 最近窗口 ≥40% 轮次含新信息
  → 1个参数，行为可预测
```

**已应用**: `data/degeneration_guard.json` — information_density 从 3 参数合并为 `info_density_min`

### 3.2 语义分层检测 (VoE 模式)

**问题**: 把所有"不符合预期"都视为错误 → 误报率高 → 用户疲劳。

**模式**: 分层检测——表面变化忽略，语义矛盾触发。

```
表面意外 (忽略):
  - 输出格式变化 (HTML vs Markdown)
  - 行数/字符数差异
  - 工具返回顺序不同
  - 日志级别波动

语义意外 (触发重规划):
  - 结果与预期矛盾 (预期"成功"但返回"失败")
  - 关键断言错误 (数据库连接被拒绝 vs 超时)
  - 数据丢失 (文件写入声称成功但文件不存在)
  - 不可逆操作 (删错了分支/文件)
```

**已应用**: `degeneration_guard.json` — `surprise_gate.surface_vs_semantic`

### 3.3 优雅降级链

**问题**: 新功能失败 → 整个系统不可用。

**模式**: 三级回退——每一级比上一级功能更少但更可靠。

```
L1: HTML Card (功能全)
  ├→ L1 失败?
  │     └→ L2: 降级文本 (功能少但可靠)
  │           └→ L2 失败?
  │                 └→ L3: 原始 Markdown (最小但永不失败)
```

**已应用**: `gateway/html_to_feishu_card.py` — `USE_HTML_OUTPUT` 三级回退链

### 3.4 恢复上限门控

**问题**: 无限重试 + 每次都是不同错误 → 系统性问题被当作单点故障反复修补。

**模式**: 累积恢复计数——超过上限 + 错误多样性 → 判定为系统性问题，触发重规划（不是重试）。

```
单任务内:
  恢复1 → 成功 → recovery_count=1 → 继续
  恢复2 → 成功 → recovery_count=2 → 继续
  恢复3 → 失败 → recovery_count=3 + 2种错误 → 🔴 系统性故障 → 重规划
```

**已应用**: `degeneration_guard.json` — `recovery_loop` + `data/recovery_bridge.json`

### 3.5 检测/执行分离

**问题**: 稳定性检测嵌入主循环 → 检测失败拖慢正常任务。

**模式**: 检测是**被动观察者**，不参与主循环。只在阈值触发时介入。

```python
# ❌ 反模式: 检测嵌入主循环
for turn in range(max_turns):
    result = execute_step()
    if is_degenerate(result):  # 每步都检查 → 拖慢
        break

# ✅ 检测分离
for turn in range(max_turns):
    result = execute_step()
    degeneration_monitor.observe(result)  # 异步观察，不阻塞

# 独立触发
if degeneration_monitor.triggered:
    evaluator_optimizer.maybe_replan()
```

**已应用**: `degeneration_guard` 是独立配置 + skill，不作为硬编码逻辑嵌入主循环

## 4. 反模式（禁止）

| # | 反模式 | 为何禁止 | 替代 |
|---|--------|---------|------|
| 1 | 硬编码重试次数 (如 `for i in range(3): retry()`) | 不同错误需要不同策略，统一重试是懒惰 | 用恢复模式引擎匹配错误类型 |
| 2 | 静默吞错 (bare `except: pass`) | 系统性问题被隐藏，最终以更严重的方式暴露 | 至少 log.warning + 递增 error counter |
| 3 | 混合阈值 (改 A 阈值影响 B 的行为) | 行为不可预测，调试噩梦 | 单参数门控 (模式 3.1) |
| 4 | 检测和执行同路径 | 检测失败 = 任务失败 | 检测/执行分离 (模式 3.5) |
| 5 | 无上限重试 | 资源泄漏，用户体验极差 | 恢复上限门控 (模式 3.4) |
