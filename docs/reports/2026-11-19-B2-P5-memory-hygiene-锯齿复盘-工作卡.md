## 5. 找 bug ①：锯齿主因是「不排程」还是「砍太狠」？（两因读数拆分）

**两因同时成立，但角色不同——不排程造成「只涨」，砍太狠放大「振幅」**：

- 「不排程」侧读数：cron `jobs.json` 中 memory/hygiene/dream 类任务 **0 个**（grep `'"name":'` 命中 0）；8 期动作量为 0 的期数 **4/8**；提纯发生点全在观察日志写下「需另起一轮提纯」之后 = 纯抢救型；上涨是**单边**的（5087→7956，7 天 +2869 ≈ **+410 chars/天**，期间 0 次下行）。
- 「砍太狠」侧读数：篇6→篇7 一刀 **−2540 chars / entries 22→10（条目级 −55%）**；且**无任何 RAW 留档**（`memories/` 下 ARCHIVE 最新 10-08、`.bak-pre*` 最新 10-07、precompact 11-16 —— 11-01→11-08 那一刀前后**无备份**）。一刀砍掉 55% 条目 ⇒ 9 天后必然回弹，回弹量 +2949 chars/9 条。
- 判定：**排程是必要条件、粒度是充分条件**。只排程不改粒度 ⇒ 变成「每周砍一刀、每周回弹」，锯齿频率上升而振幅不减；只改粒度不排程 ⇒ 依旧到期抢救。故修法必须是「排程 + 出账粒度」双改。

## 7. 找 bug ③：阈值 70/85 有依据吗？（历史分布检验）

- **85** 有真源：`scripts/check_memory_hygiene.py` `USAGE_LIMIT_PCT = 85.0`（硬编码，已有 pytest 双向回归）。
- **70 无真源，且周粒度下接近死线**：8 期周读数 5 个有效点 = 58.0 / 89.5 / 89.8 / 90.4 / 99.4 ⇒ **黄区 70-85 命中 0 次**，分布是**双峰**（要么砍到 58，要么顶在 89+）。
- **但 70 在日粒度不是死线**：12 日快照里 <70 有 4 点（63.6 / 67.6 / 68.1×2）、70-85 有 1 点（80.6）⇒ 「70-85 区」在日粒度存在，只是**被周采样错过**。
- 结论：**周粒度上的锯齿是采样+阈值滞后共同产物**；建议绿区线取 **65**（唯一 PASS 点 58.0 + 日粒度最低 63.6 之上留余量；Hermes 侧口径「留 500 字余量」= 6.25pp ⇒ 85−6.25≈78.75 不当绿线而是黄区上沿动作线），并把「增速」写成第一类触发条件。

## 9. 自审 + 边界

- 自审（归因合理性）：锯齿三因排序 = ①无排程（必要）②无知识态出口（充分·振幅放大器）③阈值采样滞后（观测层）。若只上排程不上出账：按本轮实测 2949/9 天增速，每周小提纯若仍按「删过期」操作将**无可删项**（0 条任务态）⇒ 排程空转，锯齿照旧。这是对草案的**核心修正依据**。
