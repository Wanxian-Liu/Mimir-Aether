# MimirAether Evaluator-Optimizer — 迭代改进循环

**核心铁律：单次生成靠天赋，迭代改进靠工程。**

来自 Anthropic "Building Effective Agents" 的核心模式：
> "One LLM call generates a response while another provides evaluation and feedback in a loop."

---

## 触发条件

**必须触发（硬门控）**：

| 场景 | 判定 |
|------|------|
| 非代码生成任务（写作/分析/翻译/搜索综合/规划） | 🔴 触发 |
| 输出质量直接影响决策或外部可见 | 🔴 触发 |
| 用户给出了明确的质量标准 | 🔴 触发 |

**不触发**：

| 场景 | 判定 |
|------|------|
| 纯代码任务 → 用 `test-driven-development` | ⚪ TDD 覆盖 |
| 简单查询/信息回复（一次性对错） | ⚪ 放行 |
| 执行层操作（git/terminal/file ops） | ⚪ 放行 |
| 用户明确要求"一次过"（如快速草稿） | ⚪ 放行 |

## 迭代循环

```
                    ┌─────────────────┐
                    │  1. 定义标准     │
                    │  (Criteria)     │
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
              ┌─────│  2. 生成        │◄──────────┐
              │     │  (Generate)     │           │
              │     └────────┬────────┘           │
              │              │                    │
              │     ┌────────▼────────┐           │
              │     │  3. 评估        │           │
              │     │  (Evaluate)     │           │
              │     └────────┬────────┘           │
              │              │                    │
              │        ┌─────┴─────┐             │
              │        │           │             │
              │     ✅ 通过      ❌ 未通过        │
              │        │           │             │
              │        │     ┌─────▼────────┐    │
              │        │     │ 4. 反馈       │    │
              │        │     │ (Feedback)    │────┘
              │        │     └──────────────┘
              │        │        迭代 ≤ 3 次
              │        │
         ┌────▼────────▼────┐
         │  5. 输出最终结果  │
         └──────────────────┘
```

## 执行协议

### 阶段 1：定义标准（首个 LLM 调用）

在生成之前，明确评估维度：

```
标准模板:
  1. [维度名称]: [通过条件] — [权重: 必须/重要/加分]
  2. [维度名称]: [通过条件] — [权重: 必须/重要/加分]
  ...

最少 2 个维度，最多 5 个。
"必须"维度 = 不通过则直接失败，不进入迭代。
```

### 阶段 2：生成（首个 LLM 调用）

按标准生成初版。**先求有，再求好**—初版不完美是正常的。

### 阶段 3：评估（同轮自评或独立评估）

**评估前: 退化门控预检** ← LeWM SIGReg+VoE (Session 75+)

加载 `mimiraether-degeneration-guard` 配置 (`data/degeneration_guard.json`)：
1. **循环检测**: 最近5轮同一工具≥3次无进展 → ⚠️ LOOP_DETECTED
2. **信息密度**: 最近4轮无新工具/文件/概念 → ⚠️ LOW_INFORMATION_DENSITY
3. **Surprise门控**: 执行结果语义矛盾 → 🔴 SURPRISE (跳过正常评估, 直接重规划)

预检结果作为评估报告的额外维度。

逐维度打分：

```
评估模板:
  1. [维度] ✅/⚠️/❌ — [一句话判定 + 具体引用]
  2. [维度] ✅/⚠️/❌ — [一句话判定 + 具体引用]
  ...
  N. 退化信号: ✅ CLEAN / ⚠️ [具体告警] / 🔴 SURPRISE

总体: PASS / NEEDS_WORK / REPLAN (仅 surprise 触发)
```

### 阶段 4：反馈 + 迭代（最多 3 轮）

如果 NEEDS_WORK：
- 只列出 ❌ 和 ⚠️ 的维度
- 给具体的改进指令（不是"再写好一点"，而是"X 段落缺少数据支撑，补充 Y"）
- 重新生成 → 重新评估
- 3 轮后仍未通过 → **停止迭代，输出当前最佳 + 未通过的维度清单**，交付给人决策

### 阶段 5：输出

```
最终输出格式:
  [改进后的内容]
  ───
  迭代: N 轮 | 评估: ✅ PASS / ⚠️ MAX_ITER (展示未通过维度)
```

## 关键原则

| 原则 | 说明 |
|------|------|
| 标准先于生成 | 不知道自己想要什么 → 迭代是随机游走 |
| 具体反馈 | "段落 2 缺少数据" > "不够好" |
| 上限 3 轮 | 4 轮以上 = 标准有问题或任务超出能力 |
| 停止即交付 | 3 轮未通过 ≠ 失败，是"交付 + 透明标注" |
| 诚实评估 | 自评容易放水，逐维度检查是唯一防线 |

## 与 Pipeline 的协作

```
brainstorming → plan → execute ──→ verify → ship
                          │
                          └→ [evaluate ⇄ optimize]  ← 本技能
                             非代码任务的迭代改进
```

**HWM 分层规划集成** (Session 75+): 如果 `data/active_task.json` 存在:
- 每次 optimize 后检查当前阶段验收标准
- 阶段完成 → 标记 completed，写入 active_task.json，触发阶段间门控检查
- 阶段未完成但步数超 max_steps → ⚠️ 触发重规划

| 技能 | 关系 |
|------|------|
| `mimiraether-test-driven-development` | TDD = 代码的 evaluate-optimize（测试驱动），本技能 = 通用的 evaluate-optimize |
| `mimiraether-verification` | verify = 最终收尾判断，本技能 = 中间的迭代改进 |
| `mimiraether-brainstorming` | brainstorming 的评估标准可直接喂入本技能 |
| `mimiraether-strategic-planner` | 战略层定义阶段 → 本技能在阶段内执行 + 阶段完成检查 |
| `mimiraether-degeneration-guard` | evaluate 前预检退化信号 |

## 最小示例

```
任务: 写一份技术博客介绍 MimirAether 的 Pipeline

标准:
  1. 准确性: 不虚构功能，不夸大能力 — 必须
  2. 结构: 有开头/正文/结尾三段式 — 重要
  3. 可读性: 非技术读者也能理解核心思路 — 加分

第1轮 → 生成 → 评估: 准确性✅ 结构⚠️ 可读性❌
  反馈: "段落 3-4 术语密度太高，每段加一句白话解释"

第2轮 → 生成 → 评估: 准确性✅ 结构✅ 可读性✅ → PASS

输出: [第2轮内容] + 迭代: 2轮 | ✅ PASS
```

## 反模式

1. **没标准就迭代**：生成一堆版本，但不知道哪个好
2. **模糊反馈**："再改改" / "优化一下" — 等于没反馈
3. **无限迭代**：4 轮以上还在改 → 停，交付人判断
4. **跳过评估直接交付**：改了一版就声称"好了" — 回到 verify 门控
5. **代码任务用本技能**：代码迭代用 TDD，不是自然语言评估

---

## 危险区域

1. **自评偏差**: Agent 既是生成者又是评估者 → 放水风险。逐维度逐句引用是唯一防线。
2. **标准漂移**: 迭代中忘了原始标准 → 每次评估前重读阶段 1 的标准
3. **迭代沉没成本**: "已经改了三轮了不想停" → 上限是 3，不是建议
