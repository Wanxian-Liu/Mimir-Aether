# MimirAether Brainstorming — 设计门控

**核心铁律：设计未批准之前，禁止写任何代码。**

Superpowers 最核心的教训：每次跳过设计直接编码导致的循环（改→提交→发现不对→再改），如果有硬门控就不会发生。

---

## 触发条件

**必须触发（硬门控）**：

| 用户说了什么 | 判定 |
|-------------|------|
| "实现/开发/构建/做 X"（X 涉及 2+ 文件或新模块） | 🔴 触发 |
| "加一个功能"、"改一下架构" | 🔴 触发 |
| "帮我写个 X"（X 超过 50 行预估） | 🔴 触发 |
| 任务涉及 3+ 工具调用且无现有 plan | 🔴 触发 |

**不触发（放行）**：

| 用户说了什么 | 判定 |
|-------------|------|
| "改一行"、"修 typo"、"提交" | ⚪ 放行 |
| 已批准的 plan 中的下一步 | ⚪ 放行 |
| "状态"、"检查"、"查看" | ⚪ 放行 |
| 纯信息查询 | ⚪ 放行 |

---

## 设计四阶段

### 阶段 1：澄清 (Clarify) — 最多 2 轮

**目标**：搞清楚"做什么"和"为什么"。

```
1. 用 ≤3 句话复述你理解的任务
2. 列出 ≤3 个关键假设
3. 如果任一假设不确定 → clarify() 问用户
4. 如果目标本身就模糊 → 先收敛目标再往下走
```

**反模式**：跳过澄清直接设计方案。**不清楚的需求产出错误的设计。**

**时间盒**：2 轮 clarify，超过仍未收敛 → 输出「已知 + 假设 + 最大风险」，让用户选择是继续澄清还是基于假设前进。

---

### 阶段 2：探索 (Explore) — 最多 3 个方案

**目标**：列出可选方案，不深入任何一个。

```
1. 列出 2-3 个可行方案（一句话 + 一个 tradeoff）
2. 标出「最简可行方案」（最小改动、最快验证）
3. 标出「最大风险」（如果错了代价最大的是什么）
```

格式：
```
方案 A：[一句话] — 优点：X / 风险：Y
方案 B：[一句话] — 优点：X / 风险：Y  
方案 C（如适用）：[一句话] — 优点：X / 风险：Y

推荐：方案 X，因为 [≤1 句话理由]
```

**反模式**：只给一个方案（没有选择 = 没有思考）；给 5+ 方案（选项剪刀）。

**时间盒**：3 个方案，超过 → 选项剪刀砍到 3 个。

### 领域角色增强（可选）

**仅当 prompt-armory 可用时执行**：

1. 从方案设计的问题域提取 1-3 个领域关键词
2. 调用 prompt-armory 的 search_all(query, limit=5)
3. 如果命中 score ≥ 70 的提示词/角色 → 追加建议行：
   💡 **领域角色增强**: 检测到 `{name}`（来源: {source}, 匹配度 {score}/100）。建议在后续设计中考虑引入该角色视角。
4. 如果无高分命中 → 静默跳过

**注意**：此步骤仅提供建议，不影响方案选择。角色不在 brainstorming 阶段注入，仅标记可用性。

---

### 阶段 3：收敛 (Converge) — 输出设计摘要

**目标**：把选定的方案写成可评审的设计摘要。

**如果任务预估 ≥5 步骤或 ≥3 文件**: 加载 `mimiraether-strategic-planner`，在输出设计摘要后附加阶段分解。

必须包含（控制在 20 行以内）：

```markdown
## 设计摘要：[一句话标题]

**目标**：[一句话]

**方案**：[选定的方案，2-3 句]

**改动范围**：
- 文件 1：改什么
- 文件 2：改什么
- （新增/删除标记清楚）

**不做的**：[明确边界]

**验证方式**：[怎么知道做对了]

**风险**：[最大的一个风险 + 缓解]
```

**反模式**：设计摘要写成实现文档。这是审批用的，不是执行用的。

---

### 阶段 4：批准 (Approve) — 硬门控

**这是硬门控。未经批准，禁止进入 plan-mode 或编码。**

```
1. 提交设计摘要给用户
2. 明确问：「批准这个设计吗？」
3. 用户说"可以/好/行/批准/开始" → 放行 → plan-mode 或直接执行
4. 用户说"不对/改/再想想" → 回到阶段 1 或 2
5. 用户沉默 → 不行动。不默认批准。
```

## 与 MimirAether 技能生态的协作

```
                    ┌──────────────────────┐
                    │  mimiraether-         │
                    │  brainstorming (本技能) │
                    │  设计门控              │
                    └──────────┬───────────┘
                               │ 设计批准
                               ▼
                    ┌──────────────────────┐
                    │  mimiraether-         │
                    │  plan-mode            │
                    │  任务分解              │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │  subagent-driven-      │
                    │  development           │
                    │  执行                  │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │  mimiraether-         │
                    │  verification (P1)     │
                    │  验证门控              │
                    └──────────────────────┘
```

| 技能 | 协作方式 |
|------|---------|
| `mimiraether-paralysis-break` | 每个阶段都有时间盒。如果 brainstorming 本身超过 5 分钟无输出 → paralysis-break 熔断 |
| `mimiraether-plan-mode` | 设计批准后 → 可进入 plan-mode 做任务分解 |
| `mimiraether-tool-triggers` | 本技能的触发规则与 tool-triggers 元规则联动 |
| `mimiraether-skill-solidify` | 如果设计过程中发现了新的可复用模式 → 固化 |

## 关键原则

| 原则 | 来源 | 说明 |
|------|------|------|
| 设计未批准 = 禁止编码 | Superpowers | 硬门控，不可绕过 |
| 时间盒 | paralysis-break | 每个阶段有硬上限 |
| 选项剪刀 | paralysis-break | 3 个方案封顶 |
| 最简可行方案优先 | MVA | 如果选项质量相当，选改动最小的 |

---

## 反模式与陷阱

1. **跳过门控**："这个简单，直接写就行" — 简单任务触发条件已经放过，触发了说明不简单
2. **设计过度**：把设计摘要写成 200 行实现文档 — 设计是审批用的，不是执行手册
3. **方案过载**：给 5+ 个方案让用户选 — 选项剪刀，最多 3 个
4. **默认批准**：用户沉默 ≠ 批准。必须明确问
5. **设计阶段本身瘫痪**：使用 paralysis-break 的时间盒约束
