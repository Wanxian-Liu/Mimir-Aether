# MimirAether Strategic Planner — HWM 分层规划战略层

**来源**: HWM (2604.03208) §2.3 Top-Down Hierarchical Planning | Session 75+  
**补充方法（2026-05-27 Mimir自研）**：三遍思考法 — 第1遍给出初始结论（不设防），第2遍质疑每个选择（找反例），第3遍对比前两遍得出真正答案。用于方向性决策（"该学什么"/"该修什么"/"该怎么做"），防止第一直觉片面。使用例：bridge §6.21 Hermes 20块最终结论。
**核心原理**: 单层规划在长视界任务中预测误差累积 + 搜索空间指数爆炸。解决方案：战略层(阶段分解) + 战术层(Pipeline执行) + 共享任务表示。

---

## 触发条件

**硬门控**（brainstorming 收敛阶段触发）:

| 条件 | 动作 |
|------|------|
| 任务预估 ≥5 步骤 或 涉及 ≥3 文件 | 触发阶段分解 |
| 用户明确要求"分阶段做" | 触发 |
| 任务包含天然阶段边界（设计→实现→测试→部署） | 触发 |

**不触发**：

| 条件 | 动作 |
|------|------|
| 单文件简单修改（≤3步骤） | 跳过，直接用 plan-mode 扁平分解 |
| 纯查询/状态检查 | 跳过 |

## 阶段分解协议

### 输入

```
- 用户目标（来自 brainstorming 阶段1 Clarify）
- 选定方案（来自 brainstorming 阶段3 Converge）
- 约束条件
```

### 分解规则

```
1. 识别自然阶段边界：
   - 设计/原型 → 实现 → 验证 → 清理
   - 抽取接口 → 实现核心 → 迁移调用方 → 删除旧代码
   - 基础设施 → 功能A → 功能B → 集成测试

2. 每阶段满足 HWM 子目标条件：
   - 有独立的验收标准（阶段内可判断完成）
   - 阶段内步数 ≤ 8（短视界，战术层可精确执行）
   - 阶段间有明确依赖（阶段N完成前，阶段N+1不开始）

3. 阶段数：2-5 个
   - <2 → 不需要分层，直接用 plan-mode
   - >5 → 阶段太碎，合并相邻阶段
```

### 输出格式

```markdown
## 战略分解: [任务名称]

### 阶段依赖图
```
[Phase 1: 设计契约] → [Phase 2: 核心实现] → [Phase 3: 迁移调用方] → [Phase 4: 清理验证]
```

### Phase 1: [名称]
- **目标**: [一句话]
- **验收标准**: [可验证的条件]
- **预估步骤**: N
- **最大允许步数**: N × 1.5 (超过则触发重规划)

### Phase 2: [名称]
...

### 全局约束
- **不允许**: [明确边界]
- **如果阶段失败**: 暂停后续阶段，先修复当前阶段
- **重规划触发**: 单阶段超过最大步数 或 Surprise门控触发
```

## 共享任务表示 (Shared Task Representation)

**类比 HWM 共享潜空间** — 战略层和战术层通过此结构传递子目标。

```json
{
  "task_id": "task-2026-05-14-001",
  "overall_goal": "重构认证模块",
  "phases": [
    {
      "id": 1,
      "name": "抽取接口",
      "goal": "定义 AuthProvider 抽象接口 + 类型签名",
      "accept": "接口通过 mypy 检查 + 所有现有测试通过",
      "status": "pending",
      "max_steps": 6,
      "completed_steps": 0
    }
  ],
  "current_phase": null,
  "global_constraints": [
    "不破坏现有 API",
    "保持测试覆盖率 ≥ 当前值"
  ]
}
```

**状态文件**: `data/active_task.json`（当前活跃任务的阶段状态）

## 与 Pipeline 的协作

```
                    ┌──────────────────────┐
                    │  brainstorming        │
                    │  设计门控              │
                    └──────────┬───────────┘
                               │ 方案选定
                               ▼
                    ┌──────────────────────┐
                    │  strategic-planner    │  ← 本技能
                    │  阶段分解 + 子目标生成  │
                    └──────────┬───────────┘
                               │ 阶段序列
                               ▼
                    ┌──────────────────────┐
                    │  plan-mode            │
                    │  阶段内任务分解        │
                    └──────────┬───────────┘
                               │
                               ▼
            ┌──────────────────────────────────┐
            │  战术层 (Tactical Executor)       │
            │  execute → evaluate-optimize →    │
            │  verify → [next phase or done]    │
            │  受战略层子目标约束               │
            └──────────────────────────────────┘
```

## 阶段间门控

完成 Phase N 后，进入 Phase N+1 前：

```
1. 检查: Phase N 验收标准是否全部满足？
   ├── ✅ → 标记 Phase N completed
   │        更新 data/active_task.json
   │        进入 Phase N+1
   └── ❌ → 不推进。修复当前阶段或重规划。

2. 检查: Phase N+1 的子目标是否仍然有效？
   ├── ✅ → 继续
   └── ❌ → 战略重规划（可能阶段序列需要调整）

3. 检查: 是否触发了 Surprise 门控？
   ├── ✅ → 重规划（不仅是当前阶段，可能需要调整阶段序列）
   └── ❌ → 继续
```

---

## 反模式

1. **阶段太碎** — 4步一个阶段 → 合并且用 plan-mode
2. **阶段太少** — 1个阶段包含20步 → 分解不足，分层无意义
3. **无验收标准** — "把认证做好" → 无法判断阶段完成
4. **忽略门控** — 阶段未完成就跳下一阶段 → 累积错误
5. **战略层直接写代码** — 战略层只产出子目标，不产出代码
