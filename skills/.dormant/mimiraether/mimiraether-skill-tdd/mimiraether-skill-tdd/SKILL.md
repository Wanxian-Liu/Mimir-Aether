# MimirAether Skill TDD — 测试驱动的技能编写

**核心铁律：先证明技能是需要的，再写技能。**

当前 `skill-solidify` 的流程是「跑通了 → 固化」。Superpowers 指出这不够：**你必须在固化之前证明——没有这个技能，agent 会失败。**

---

## 三阶段流程

### 阶段 1：观察失败 (Observe Failure)

**目标**：在没有技能的情况下，让 agent 面对同类任务，记录失败模式。

```
1. 识别潜在技能场景：「下次还会遇到吗？会 →」
2. 在固化之前，先问：「没有这个技能时，agent 怎么失败的？」
3. 如果 agent 没有这个技能也能正确处理 → 不需要技能
4. 如果 agent 反复犯同样的错误 → 需要技能
```

**记录格式**：
```
失败模式：[agent 做了什么错误的]
根因：[缺少什么知识导致]
频率：[每次/经常/偶尔]
成本：[每次失败浪费多少时间/工具调用]
```

**反模式**："我觉得这个会有用" — 感觉不是证据。必须观察到实际失败。

---

### 阶段 2：写技能修复 (Write Skill to Fix)

**目标**：写的每一条指令都必须对应一个观察到的失败。

```
1. 回顾失败记录
2. 对每个失败模式，写一条指令
3. 指令格式：「当 X → 做 Y」（不是「注意 X」）
4. 不在技能里写「没观察到失败」的内容
```

**对照检查**：
```
失败模式                    →  技能指令
─────────────────────────────────────────
agent 跳过设计直接编码        →  触发条件 + 阶段 1-4
agent 提交前不验证            →  验证四层
agent 在循环中不察觉          →  强制觉察触发器
```

**反模式**：
- 写"最佳实践"而非"修复已知失败"
- 技能里有「以防万一」但没有对应失败的规则
- 从 superpowers 复制内容但不验证 MimirAether 是否有同类失败

---

### 阶段 3：验证修复 (Verify Fix)

**目标**：证明技能确实阻止了失败。

```
1. 加载新技能
2. 重现原来的失败场景
3. 确认 agent 这次做了正确的行为
4. 如果没有 → 技能不够，回到阶段 2
5. 如果通过 → 固化完成
```

**验证标准**：不是"技能写得好不好"，而是「agent 是否不再犯同样的错误」。

---

## 与 skill-solidify 的关系

```
skill-solidify (现有)          skill-tdd (本技能)
─────────────────────────────────────────────────
跑通 → 固化                    先观察失败 → 再固化 → 再验证
"下次会用到"                    "没有它 agent 已经失败了"
事后记录                       事前证明
```

**不替代 skill-solidify**，而是给它增加一个前置步骤：固化之前，先走 TDD 三阶段。如果 agent 在这个场景下从未失败过 → 也许不需要技能。

---

## 何时升级到 TDD

| 场景 | 用 skill-solidify | 用 skill-tdd |
|------|-------------------|-------------|
| 新工具的使用命令 | ✅ 够用 | 不需要 |
| 复杂工作流（3+ 步骤） | ✅ 够用 | 可选 |
| 行为约束/门控 | ❌ 不够 | ✅ 必须 |
| 反复出现的错误模式 | ❌ 不够 | ✅ 必须 |
| 流程/管道技能 | ❌ 不够 | ✅ 必须 |

**简单说**：
- 「怎么用 X 工具」→ skill-solidify 够用
- 「不要在做 Y 之前忘了 Z」→ 必须 TDD

## 实战示例：brainstorming 的 TDD 过程

### 观察到的失败

```
失败模式：agent 收到"加 MAX_MESSAGE_LENGTH"→ 直接改代码 → 提交 → 用户说循环了
根因：没有设计门控，agent 跳过"问清楚再动手"
频率：每次复杂任务
成本：整个会话陷入循环，浪费 10+ 轮
```

### 技能修复

```
触发条件：用户说"实现/加/做" → 进入设计四阶段
硬门控：设计未批准 → 禁止编码
时间盒：每个阶段有上限（与 paralysis-break 联动）
```

### 验证

```
重现：用户说"帮我加个功能" → agent 先进入设计阶段而非直接编码 ✅
```

## 关键原则

| 原则 | 来源 | 说明 |
|------|------|------|
| 先失败再固化 | Superpowers | 没有观察到的失败 = 不需要技能 |
| 每条指令对应一个失败 | Superpowers | 不写"以防万一" |
| 验证的是行为变化 | Superpowers | 不是文档质量，是 agent 是否真的不再犯错 |
| 行为约束必须 TDD | 自身教训 | brainstorming/verification 这类门控不能用 skill-solidify |

---

## 反模式与陷阱

1. **凭空写技能**：没有观察到失败就觉得"应该有用" → 浪费 token
2. **复制但不适配**：从 superpowers 复制但不验证 MimirAether 是否有同类失败
3. **技能验证只靠读**：`skill_view` 看一遍就完了 → 必须重现失败场景
4. **过度 TDD**：简单命令工具不需要 TDD，skill-solidify 够用

### Beyoncé Rule（碧昂丝规则）

> *"If you liked it, you should have put a test on it."*
> — 碧昂丝·诺尔斯，经由 addyosmani/agent-skills 引入开发流程

**含义：** 基础设施、重构、迁移、配置变更——凡是变更后可能出问题的东西，都应该有测试。不是因为"写测试是好的"——是因为"没有测试 = 无法证明没坏"。

**在我们的上下文中：**
- 重构 skill 后 → 必须 `skill_view` 验证 + 重现失败场景验证
- 修改行为约束后 → 必须触发原失败模式，确认被阻止
- 添加新 skill 后 → 必须走 Observe Failure → Write Skill → Verify Fix 三阶段

**违反 Beyoncé Rule 的后果：** 你这次改的东西，下次一定坏——而你不知道它已经坏了。
