# Patterns — 模式与反模式

## 正面模式
| 模式 | 何时用 | 做法 |
|------|--------|------|
| **验证先于建造** | 任何建造前 | 会话/证据先于代码；原型只作压力测试工具 |
| **持久上下文** | 从MVP第一天 | specs + CLAUDE.md + 每会话更新 |
| **三面配合** | 全周期 | Chat快问 / Cowork研究+自动化 / Code写码，输出互喂 |
| **先审计后系统化** | Launch | 全量清单→分类系统化/委托/保留 |
| **瓶颈图** | Scale | 外推"消失一周"识别亲力亲为的阻塞点 |
| **护城河深度** | 全周期 | 一致方向+一致基础设施→难复制的累积深度 |

## 反模式（AI时代被放大的）
| 反模式 | 为什么危险 | 解药 |
|--------|-----------|------|
| **把建造当验证** | 42%失败因造了没人要的东西 | 原型≠证据，用户对话才是 |
| **过早扩张** | 执行远超验证，方向没验证就commit | sense-making跑在building前 |
| **确认偏误+AI** | AI会为你的信念找支持证据 | 同一工具反方向用：压力测试 |
| **零摩擦范围蔓延** | 每功能都合理但产品蔓延 | 建造前写范围定义+修订标准 |
| **不安全上线** | 能工作的代码≠安全代码 | 任何用户碰前安全审查 |
| **创始人瓶颈** | 1小时决策变1周 | 全量审计+系统化 |
| **技术债到期** | MVP债在Launch计息 | 架构审计+定向重构+测试扩展 |
| **未就绪扩张** | 新市场≠增长，是PMF坟场 | 扩张前安全合规审查（必修） |
