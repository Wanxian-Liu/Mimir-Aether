# Chapter 6 — Scale Stage

## 目标
从builder到public-facing executive。产品仍核心，但日常工作日益关于公司本身。保持精益AI中心结构优势的同时扩大注意力。

## 退出标准（阈值事件——三种形态之一）
1. 可持续盈利（无需外部资本）
2. IPO就绪
3. 被收购
三者都要求：增长系统化可审计、产品护城河经得起审视、组织运营成熟可持续。终极问题："**如果资金充足的巨头今天复制你的产品，你的用户会留下吗？**"

## 盈利模式与组织规模（2026-05-14 版 PDF 增补——Mimir 概念卡提炼）

- **"小而密"组织**：8-15 人是最佳规模——超过临界点组织成本消解 AI 红利；每个人必须是"被 AI 放大的人"
- **商业模式演进**：从"卖工具"→"卖服务"，向**按效果付费 / revenue share** 转变（Anthropic 自身 B2B 为范例：70-85% 收入来自 API 调用，SaaS 企业贡献 65%+ API 收入，联合开发收入分成 20-40%）
- **护城河四件套**：
  1. **领域知识沉淀**：把创始人/行业专家的隐性知识编码为 AI context（skills/记忆/边缘用例测试集）——通用 AI 无法复制
  2. **数据飞轮**：用户行为信号→产品改进→更多使用→更多反馈（时间锁定、上下文特定、无法购买）
  3. **工作流锁定**：用户在你的产品上建的自动化/提示词/集成 = 切换成本变成"整个运营迁移项目"
  4. **集成深度**：API/webhooks/SDK 让客户建在你的产品上——最深的锁定形式
- **案例**：Carta Healthcare（临床抽象平台，年处理 22,000 外科病例，数据抽象时间 -66%）、Anything（150 万用户，无代码创始人卖出完整招聘平台）、GC AI（法律）、Duvo（采购/供应链 Agent）、Wordsmith（合同审查）

## 反模式/挑战
- **委托运营层**：Scale运营系统必须无保姆可靠运行。交接太多太快→关键决策失去创始人的关键上下文；握太久→成为瓶颈。核心：识别只在创始人脑中的机构知识，编码成可记录、可审计、可转移的系统
- **建GTM功能**：有机增长有天花板。迹象：用户曲线平、获客成本升、管道只有创始人亲自参与才动
- **规模化技术运营**：客户不只评估产品，他们想知道组织是可依赖的基础设施伙伴
